# NOKOV 光学动捕文件分析报告

**原始资料分析范围：** NOKOV 交付目录；独立整理结果位于本项目  
**分析日期：** 2026-08-26  
**分析方式：** 只读检查目录、文档、配置、CSV 表头与记录数、SDK 示例、文件头和 SHA-256；未连接现场硬件。

## 1. 结论先行

这批文件由四部分组成：

1. **XINGYING/NOKOV 软件安装包**：用于相机管理、标定、采集和 Data Adapter 数据输出。
2. **NOKOV Python SDK**：用于实时接收 MarkerSet、刚体、骨骼、未识别点、模拟量和测力台数据。
3. **CalWand/CalFrame 标定工程**：保存六台相机的标定棒采集、参考坐标系采集、镜头模型和相机参数。
4. **NOKOV–MANUS B-V4 联合标定工程**：把 NOKOV 腕系下的三个光学标记点转换到 MANUS 腕坐标系，并处理指尖安装偏移与两套系统的时间延迟。

当前应使用的唯一联合标定版本是 **B-V4**。来源数据上的全数据 RMS 为 **3.671 mm**，留出验证 RMS 为 **3.899 mm**；两组独立数据的固定参数 RMS 分别为 **4.821 mm** 和 **7.539 mm**。因此，3.671 mm 是特定佩戴和动作范围下的拟合结果，不是所有动作和重新佩戴后的精度保证。

术语上，这套系统更准确地说是“**光学动捕反光标记点**”。`SinglePoint0/1/2` 是三个单点 MarkerSet，不是带姿态的刚体，也通常不是主动发光光源。

## 3. CalWand 与相机标定文件

### 3.1 文件作用判断

| 文件 | 分析结果 |
|---|---|
| `CalWand.cap` | 标定棒采集工程入口或工程描述，属于 NOKOV 私有二进制格式 |
| `CalWand/CalWand/CalWand.vc0`～`.vc5` | 六台相机的标定棒采集数据；均以 `VCRW` 文件头开头 |
| `CalFrame.cap` | 参考坐标系/标定框采集工程入口 |
| `CalFrame/CalFrame/CalFrame.vc0`～`.vc5` | 六台相机对应的 CalFrame 数据；每个文件只有约 120～168 字节，像是极短记录或仅含头信息 |
| `setup.cal` | 相机系统标定参数，NOKOV 私有二进制格式 |
| `LModel.cal` | 镜头模型或畸变相关标定数据，私有二进制格式 |
| `Tracker0.mars`、`Tracker1.mars` | 跟踪器/刚体定义或相关模型，私有二进制格式 |
| `Scenes.json` | 可视化场景模型表，当前只有 sphere、cube、ring、conethree，没有 actor |
| `analog.ini` | 模拟量、测力台和 Delsys EMG 配置；其中 EMG IP 为 `10.1.1.198` |

Linux 的 `file` 命令把 `.cap` 误识别成 OpenPGP Public Key，但文件头和同目录结构表明它是 NOKOV/XINGYING 私有工程文件，不能按 PGP 密钥处理。

### 3.2 CalWand 数据是否看起来完整

`CalWand.vc0`～`.vc5` 的体积约为 1.06～1.96 MB，说明六台相机都保存了实际采集内容。`CalFrame.vc0`～`.vc5` 只有很少数据，需要在 XINGYING 中打开工程确认是否为正常的单帧/短帧参考坐标系采集。如果软件提示数据为空或无法重建坐标系，应重新采集 CalFrame。

这组文件的意义是建立“相机像素观测 → NOKOV 世界坐标/跟踪坐标”的关系；后面的 B-V4 则建立“`newTracker2` 腕坐标 → `ManusWrist` 腕坐标”的关系。两层标定不可互相替代。

## 4. NOKOV Python SDK

SDK 示例默认连接：

```text
10.1.1.198
```

基本程序通过 `PySDKClient.Initialize()` 连接 XINGYING/NOKOV 服务，并支持回调或主动读取两种方式。每帧能够取得：

- 帧号、设备时间戳和 timecode；
- MarkerSet 及其三维点，单位 mm；
- 刚体位置和四元数，四元数顺序为 `qx,qy,qz,qw`；
- 骨骼段、未识别标记点；
- 模拟量、测力台数据；
- 扩展的速度、加速度和欧拉角数据。

SDK 包目录名为 `4.1.0.5645`，示例打印文本为 `4.0.0.5645`，分发包名为 `nokovpy-3.0.1`。这些编号来自不同层（交付包、示例文本、Python 包），部署时应以实际 `PyNokovVersion()` 输出和能否连接当前 XINGYING 服务为准。

示例中有两个明显注意点：

1. 服务器 IP 是硬编码默认值，换电脑或换网段时必须修改或使用 `-s/--server`。
2. 回调里逐帧大量 `print` 会拖慢高频采集；正式记录程序应使用队列、批量落盘或限频日志。

## 5. B-V4 联合标定的数据链

对象映射如下：

| 部位 | NOKOV | MANUS | MANUS 节点号 |
|---|---|---|---:|
| 腕部参考 | `newTracker2` | `ManusWrist` | 0 |
| 食指 | `SinglePoint0` | `ManusIndexTip` | 9 |
| 中指 | `SinglePoint1` | `ManusMiddleTip` | 14 |
| 无名指 | `SinglePoint2` | `ManusRingTip` | 19 |

处理关系为：

```text
NOKOV 相机标定
    ↓
NOKOV 世界坐标中的 newTracker2 + SinglePoint0/1/2
    ↓ 计算相对 newTracker2 的位置
NOKOV 腕坐标点 p_N
    ↓ 公共刚体外参 R、t
ManusWrist 坐标中的 NOKOV 预测点
    ↕ 与 MANUS 指尖位置比较
MANUS 原始指尖 + 指尖局部姿态旋转后的逐指 offset
    ↑
严格同步对 + pair shift = +4（约 39.90 ms）
```

最终公式是：

```text
NOKOV：p̂_N = R × p_N + t
MANUS：p̂_M = p_M + R_tip × d_f
目标：p̂_N(i,f) ≈ p̂_M(i+4,f)
```

这里的 `d_f` 是各指尖自身局部坐标中的三维向量，不能直接当作 `ManusWrist` 坐标的固定 XYZ 平移。

## 7. 三组采集数据质量与精度

### 7.1 采集完整性

| 数据集 | NOKOV 帧 | MANUS 帧 | 同步对 | 20 ms 内 | 平均绝对时间差 | 状态 |
|---|---:|---:|---:|---:|---:|---|
| `171852_336` | 1077 | 1208 | 1077 | 1077（100%） | 2.497 ms | complete |
| `171915_572` | 3505 | 3594 | 3505 | 3496（99.74%） | 3.085 ms | complete |
| `172019_231` | 1791 | 1792 | 1791 | 1788（99.83%） | 3.092 ms | complete |

三组采集文件行数与 `metadata.json` 中的 `rows` 一致，结构上完整。它们没有硬件同步，`frame_sync.csv` 只是用同一台电脑的接收时间做最近邻配对。

### 7.2 B-V4 精度

| 数据 | 食指 RMS | 中指 RMS | 无名指 RMS | 三指总体 RMS | 解释 |
|---|---:|---:|---:|---:|---|
| 来源数据前 23 s | 3.397 mm | 3.403 mm | 4.161 mm | **3.671 mm** | 全数据重拟合，不代表泛化 |
| 留出验证 | — | — | — | **3.899 mm** | 模型内部验证 |
| 独立数据 `171852_336` | 5.175 mm | 4.507 mm | 4.757 mm | **4.821 mm** | 可用，但比来源数据差 |
| 独立数据 `172019_231` | 7.684 mm | 6.873 mm | 8.013 mm | **7.539 mm** | 泛化明显下降 |

已有诊断已排除三指编号接反、严重坏帧和 `+4` 完全错误。误差升高的主要原因更可能是：

- 固定的逐指 offset 对分指、侧摆等新动作覆盖不足；
- 手套重新佩戴后的旋转或滑移；
- 指尖反光点固定位置或方向变化，尤其是无名指；
- MANUS 指尖姿态模型与真实标记中心的关系随动作变化；
- 实时程序用“缓存 4 个 NOKOV 到达帧”近似离线 `+4` 同步对，会增加瞬时抖动。

## 8. 四类采集文件如何读

### `dual_pose_frames.csv`

双源原始长表，每行是某一源的一帧中的一个对象。关键字段包括 `source`、`frame_no`、`asset_name`、有效标志、接收时间、绝对位姿和相对腕部位姿。位置单位是 mm，四元数顺序是 `xyzw`。

原始表没有写入最终 offset，应保持不变，后处理只能应用一次外参和一次 offset。

### `frame_sync.csv`

每个 NOKOV 帧与最近 MANUS 帧的接收时间配对。离线分析优先使用：

```text
matched = 1 且 within_tolerance = 1
```

配置里的 `+4` 是同步对序号移位，不是 CSV 的四行偏移，也不是 NOKOV 原始帧号加 4。

### `metadata.json`

用于判断一次采集是否完整，包含状态、帧数、行数、同步质量、对象映射和 offset 是否写入原始表。`status=complete` 只表示程序正常结束，不表示标定精度合格。

### `events.csv`

记录开始、暂停、继续、完成和派生数据集等事件，可用来恢复动作时间线。

## 9. 已发现的文件与交接问题

1. **两个“最终标定方案”ZIP 不是同一个文件。** 根目录 ZIP 为 4,921,414 字节、51 个条目，SHA-256 为 `7c352c...922a`；交接资料内 ZIP 为 4,953,336 字节、53 个条目，SHA-256 为 `60bdff...fa59`。后者与完整性文档一致，应作为正式版本。
2. **根目录解压目录出现中文乱码。** 这是 ZIP 文件名编码/解压工具兼容问题，容易导致启动脚本或人工查找出错。优先用支持中文文件名的 Windows 解压工具解压交接资料内 ZIP。
3. **交接总览中的快速上手链接文件名不一致。** 总览写的是 `01_接手人快速上手.md`，实际文件是 `01_总览b.md`；它的正文标题确实是“项目接手人快速上手”。建议后续统一文件名和链接。
4. **版本组合较多。** Windows XINGYING 为 4.6.0.7923、Linux 为 3.4.0.6843、SDK 目录为 4.1.0.5645。现场升级或换系统前应先做 SDK 连接和字段兼容测试。
5. **实时网络配置依赖现场。** B-V4 实时程序默认数据适配器为 `169.254.144.146`，并优先尝试 SDK 控制端点 `10.1.1.198`。换网卡或网段后需要检查两处配置。
6. **最终程序主要面向 Windows。** `.cmd`、PowerShell、`ManusLiveBridge.exe` 和 `ManusSDK.dll` 都是 Windows 工作流；Linux 安装包不能直接替代 MANUS 实时桥接程序。

交接资料内四个关键文件的 SHA-256 已复核，与 `04_文件完整性校验.md` 完全一致。

## 10. 推荐使用顺序

1. 从 `NOKOV_MANUS_20260811/00_交接总览.md` 开始阅读。
2. 把 `NOKOV_MANUS_20260811/01_总览b.md` 当作当前的快速上手说明。
3. 使用交接资料内的 `B-V4最终标定方案_代码与可视化包_20260807.zip`，不要混用根目录旧 ZIP。
4. 在 Windows 上先运行 `00_检查运行环境.cmd`，再运行 `01_查看示例数据_双击.cmd`。
5. 离线示例应得到约 3.671 mm 总体 RMS；明显偏离时检查配置是否读错或 offset 是否重复应用。
6. 连接硬件后确认 XINGYING 中存在 `newTracker2` 和 `SinglePoint0/1/2`，并核对三指映射。
7. 新采集先做“固定参数评估”，不要先重新拟合；这样才能判断 B-V4 的真实泛化效果。
8. 若移动了腕部刚体、指尖标记、更换手套或重新佩戴后误差持续升高，应重新采集覆盖静态张手、单指屈曲、同时屈曲、分指和并指的数据，再重新标定并用独立数据验证。

## 11. 最终判断

文件整体上是一套结构完整、文档较充分、可复现的 NOKOV–MANUS 联合标定交付。NOKOV 采集本身的同步可用率很高，当前主要工程风险不在“光学数据缺失”，而在 **两套系统没有硬件同步、指尖局部 offset 的动作泛化、重新佩戴一致性和反光点安装稳定性**。

如果目标只是运行和查看，应锁定 B-V4 交接包。如果目标是进一步把独立数据稳定到 3～5 mm，应优先改进现场标记安装、动作覆盖和基于时间戳的实时缓冲配对，然后再考虑更复杂的逐动作或非刚性补偿模型。
