## 2. 使用的时间字段

四组数据中的 NOKOV 时间字段表现为：

```text
device_timestamp_raw：约 1.787824e12
相邻帧中位增量：11
采集帧率：90 Hz
```

它与同帧 `receive_unix_ns` 对应的 Unix 时间一致，量级和增量均表明该字段是 Unix epoch 毫秒时间戳。因此本次使用：

```text
nokov_time_s = device_timestamp_raw * 0.001
```

同步命令必须包含：

```text
--nokov-time-field device_timestamp_raw
--nokov-time-scale 0.001
```

`receive_perf_ns` 是 SDK 客户端本机的单调接收时钟，只用于诊断或在设备时间不可用时回退。

约18.7秒处 NOKOV 角速度出现约5.1 rad/s的单次异常尖峰，而 EGO 同期峰值明显较小。这可能是刚体姿态瞬时抖动、快速运动差分放大或短暂重建跳变。该 session 可用于联调，不建议作为精度基准。

## 6. 绝对时间戳与运动同步的差异

如果只使用 EGO 和 NOKOV 两个起始绝对时间戳直接相减，得到的偏移与运动相关结果并不一致。同一运动对应时：

| Session | NOKOV设备时间戳 − EGO IMU时间戳 |
|---|---:|
| `001` | -384.7 ms |
| `002` | -390.1 ms |
| `003` | -420.4 ms |
| `004` | -420.9 ms |

四组均显示 NOKOV 设备时间戳相对 EGO IMU 时间戳约早0.4秒，并且差值随实验时间变化。因此：

- 不能仅靠文件名或绝对时间戳直接配帧；
- 必须使用共同运动信号估计时间关系；
- 设备时间戳仍应保留，用于建立每套系统内部的连续时间轴。

若改用 NOKOV SDK 客户端的 `receive_unix_ns`，同一运动对应的时间差约为 `-164～-182 ms`。这反映客户端接收时钟和设备测量时钟定义不同，不能把它直接解释为单一网络延迟。

CSV 历史字段名 `sdk_latency_s` 中的数值约为 `2.4～16.3`。厂家公开资料和当前 SDK Python 定义没有明确给出该字段单位，本报告不把它当作秒，也不使用它修正时间轴。

## 7. 初步时钟漂移观察

四组 session 起点跨度约333秒。以每组运动相关结果作为跨系统对应观测，线性拟合得到一个初步趋势：

```text
NOKOV device clock relative to EGO：约 -124 ppm
拟合残差 RMSE：约 4.8 ms
```

这是由四个独立短 session 推断的初步结果，可能同时包含每次相关估计误差和系统延迟变化，不能代替正式连续录制的 `a`。

正式估计应使用同一个3～5分钟 session，在开头、中间和结尾执行不同同步动作，拟合：

```text
t_nokov = a * t_ego + b
```
